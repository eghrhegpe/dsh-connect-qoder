# 明文 OSCrypt 主密钥残留在共享 %TEMP%

**P0 · 规模 S · 依赖 —（与 #01 同一片代码，建议同 PR）**

## 症状

解包失败时 `key.b64` 会原样留在 `%TEMP%\qoder-oscrypt-*`，而唯一的回收点是**下次插件启动**的 sweep
（没有定时器）。文件内容是 OSCrypt 主密钥的 base64——凭据级材料。

## 证据

- `lib/credentials.js:260-342`（`oscryptKeyFor` 的 `finally` 清理；失败不缓存但会留下临时目录）
- `lib/index.js:592-601`（启动时 sweep 是唯一调用点）
- 本机实测：`%TEMP%\qoder-oscrypt-j5lTke\key.b64` = **48 字节全非零**

## 修法

1. 清理失败时立刻重试一次；
2. 仍失败则**先把文件截断为 0**（"剩 48 字节明文"比"删不掉"更糟）；
3. `process.on('exit')` 路径里补一次扫描；
4. 残留出现时通过 `setCredentialDiagnosticSink` 上报（含 TTL/年龄）。

## 实现（部分修复，两处偏离原方案）

**已做**：

- `zeroOutFile` 重试全部失败后，落盘前追加一次 `truncateSync(file, 0)` 最后手段，
  随后仅当"文件仍在且长度 > 0"才上报——截断成功即危险解除，不再谎报。
  （重试本已存在：4 次、线性退避，即原方案第 1 条。）
- 上报通道沿用 `reportCleanupFailure` → 诊断 sink（原方案第 4 条，此前已成立）。

**偏离 1 —— 截断在 Windows 上大概率无效（实测，非推测）**：本机实验证明
`FileShare.None` 句柄同样挡住 `truncateSync`（EBUSY）、`unlinkSync`（EBUSY）、
`rmSync`（EPERM），因为 Node 的 truncate 也要先以写权限打开文件。工单证据场景
恰恰是"子进程被杀、句柄未及释放"——所以截断兜底在该场景救不了 Windows，
真正的缓解是上面的重试窗口等来内核拆除 + 下次启动的 sweep。它在 POSIX
（锁语义不同）和非句柄类失败上仍然有效，故保留为廉价的最后手段。
验收标准第 1 条（"锁定后长度必须为 0"）**在 Windows 上无法达成**，不强测；
锁定场景仍由既有用例断言"必须产生上报 + 兄弟目录仍被回收"。

**偏离 2 —— 不做 `process.on('exit')` 扫描**：模块里已有的 exit 钩子只做内存
清零，文件扫描要把整个 sweep 逻辑接进进程退出路径，事件循环已死、句柄未必
释放（正是本工单自己描述的失败模式），收益存疑、复杂度实在。残留的正式
认领者是启动 sweep；本仓库的规矩是把"没做什么"写下来，此句即是。

## 验收标准

- [~] 模拟"文件被独占句柄锁住"：~~该次调用后文件长度必须为 0~~ —— Windows 上
      截断与删除被同一把锁挡住（实测 EBUSY），无法达成；改为断言锁定场景
      **必须产生可被诊断 sink 收到的上报**（既有用例已覆盖，本次继续通过）
- [x] 残留出现时产生一条可被诊断 sink 收到的上报
- [x] 正常路径仍然删除整个临时目录（不回退行为）
